# Reading Surface Plan — August 2026

A frontend pass on the build at `33c9fd6`, from screenshots of `Docs/sample.md`
in Document mode plus a read of the render sources.

**Relationship to `Docs/UI-PLAN.md`:** that plan was written against `8d2855b`
and has largely shipped — it describes the app in the screenshots. This document
does not supersede it wholesale. Where the two disagree, this one is newer.

**Relationship to `DESIGN.md`:** none. `DESIGN.md` is stale and is explicitly
*not* authoritative for this pass. Every recommendation below is argued from
what produces the better experience, not from what a document says. Several
items reverse what `DESIGN.md` asks for. Do not resolve a question in this plan
by consulting `DESIGN.md`.

**How to use this:** each item is a self-contained unit of work with a
`Done when` you can check. Items are ordered within a section by dependency, and
the sequencing in §7 is the recommended commit order. Nothing here requires a
design decision that has not already been made — §1 lists the locked ones with
their reasoning, so you can tell an implementation detail from a reversal.

## 1. Locked decisions

These were decided with the product owner. The reasoning is recorded so that an
implementer can tell when a detail is negotiable and when it is not.

| # | Decision | Reasoning |
|---|---|---|
| L1 | **The density rail stays on the left, unchanged.** | It is a scrollbar thumb made of document shape: the cluster's vertical position in the window *is* the scroll position, and its marks are the local document structure. Expanding it to full height would turn an elegant position indicator into a busy minimap and lose that. Its only change is L6. |
| L2 | **Remove the marker lane entirely** — the `#`, `##`, `$$`, `---` glyphs hanging left of the column. | They are source spelling shown in the rendered view. Heading size and weight already carry level, and the lane costs horizontal offset that pushes the whole column off the window's axis. |
| L3 | **Heading level gets an actual control, not a decorative marker.** | Seeing `##` does not help you change a heading; it only tells you what you already inferred from its size. The need behind the marker is *restructuring*, so ship the mechanism (keyboard + a clickable level chip) rather than the symptom. See S2. |
| L4 | **Footnotes render in the right margin, beside their reference.** | Following a footnote today costs you your place in the document. This is the single best use of the empty space, and it makes finding D2 load-bearing rather than cosmetic. |
| L5 | **The section label is a proxy for a heading that scrolled away.** | Therefore it belongs where that heading was — left, on the text column's axis — and it must not appear while the heading itself is still on screen. See S3. |
| L6 | **The rail's hover preview shows heading + first sentence**, not raw markdown. | Someone navigating a rendered document wants to know what is there, not how it is spelled. `StructuralZoom.skeletonExtras` already computes exactly this. |

### Two calls made on the owner's behalf

Both were left to my judgement. Recorded here with full reasoning so they can be
reversed cheaply if the reasoning does not hold up in practice.

**S3 — the section label.** The question was whether to keep the centred pill,
left-align it, or replace it with the real heading docking to the top. The
answer is a hybrid, and it hinges on a rule none of the three options stated:
*the label should not exist while its heading is visible.* In screenshot 3 the
`Callouts` heading is on screen **and** the label says `Callouts` — the app is
saying the same thing twice, in two typefaces, in two places. That is the actual
defect. Once the label only appears when it is doing work, the remaining
question is small: keep the quiet pill treatment (it handles nested headings and
carries the path menu, both of which a docked H2 handles badly) but put it on the
text column's left edge, because it stands in for a heading and headings are
left-aligned there.

**S2 — heading markers while editing.** The owner's instinct was right on all
three counts: a read-only `##` does not help, an inline `##` that shifts text is
bad motion, and Source mode makes a pure viewer redundant. All three framings
were wrong because they assumed the answer had to be *a marker*. The user need
is "make this H2 an H3", and the mechanism for that is `⌘]` / `⌘[` plus a
clickable `H2` chip — semantic level, not source spelling, and editable, which
is what makes it earn its space.

## 3. Defects

The app contradicting itself. Cheap, and each one is individually visible in a
screenshot.

### D1 — The task ring reports no count, and reads as complete when it is not

**Evidence.** All three shots are the same document, which has 5 tasks done and
1 open (`Sparkle appcast`, shot 3). The toolbar ring renders as a closed amber
circle with an empty centre — visually identical to what "all done" should look
like.

**Why it matters.** A permanent toolbar element that shows a filled circle
regardless of state is not status, it is decoration — and worse, it is
*wrong* status. The number of tasks still open is the figure a reader acts on;
a proportion is not.

**Change.**
- Arc sweeps from twelve o'clock to `done / total`, proportionally.
- Remaining count (`total - done`) crossfades in the ring's centre.
- All done: ring closes, count is replaced by a check.
- No tasks: quiet empty track, no fill, still clickable.

**Files.** `Panels/TaskProgressRing.swift`

**Done when.** Opening `Docs/sample.md` shows a ring roughly 5/6 swept with a
`1` in its centre. Ticking `Sparkle appcast` closes the ring and swaps to a check.

---

### D2 — Footnote references render literally as `^1`

**Evidence.** Shot 1: "as do footnotes^1". A caret and a digit sitting in the
prose as plain characters.

**Why it matters.** It is a visible parse failure in the sample document the
project uses to sanity-check builds. It also blocks S4 — margin footnotes need a
reference to anchor to.

**Change.** Confirm the reference is being consumed by the parser. Render as a
true superscript at ~62% of body size, in the accent colour, with a hit target
large enough to click.

**Files.** `MarkdownCore/Parser.swift`, `Engine/DecorationEngine.swift`

**Done when.** `footnotes[^1]` renders as a superscript ¹, and clicking it moves
to the note.

---

### D3 — A wrapped table cell breaks the row rhythm

**Evidence.** Shot 2, modes table: the gap between `Read` and `Live` is visibly
larger than the gap between `Live` and `Source`, because `Read`'s two-line
Purpose cell adds trailing space no other row pays.

**Why it matters.** Every real table has wrapping cells. The rows stop reading
as a grid.

**Change.** Row height = `max(cellHeight) + 2 × verticalPadding`, with padding
applied symmetrically per row. The extra line currently appears to land inside
the row box rather than growing it evenly.

**Files.** `Fragments/TableFragment.swift`

**Done when.** In shot 2's table, baseline-to-baseline distance between the first
line of each row is equal for all rows with equal line counts, and rows with
extra lines grow symmetrically.

---

### D4 — The section label duplicates a heading that is already on screen

**Evidence.** Shot 3: the label reads `Callouts ⌄` while the `Callouts` heading
sits ~50pt below it, fully visible.

**Why it matters.** This is the root defect behind the section label, and it is
why the element reads as chrome rather than as help. It should only exist when
the heading it names has left the viewport.

**Change.** Show the label only when the current section's heading is scrolled
above the top of the content area. Fade in over 0.12s on the boundary crossing,
fade out the same way. A document scrolled to the top shows no label at all.

**Files.** `App/DocumentWindowController.swift` (the scroll-boundary tracking
around line 882), `Panels/BreadcrumbView.swift`

**Done when.** Scrolling `sample.md` so `Callouts` is visible shows no label;
scrolling until it passes the top fades one in.

---

### D5 — The section label has no backdrop, so content scrolls under it

**Evidence.** Shot 2: the table's header row clears the label by roughly 15pt.
At a different scroll offset they overlap outright.

**Change.** Behind the label, paint the page ground at full opacity, fading to
transparent over ~24pt below it. Because of D4 the scrim is only ever visible
when the label is, so a top-of-document view stays completely clean.

**Files.** `App/DocumentWindowController.swift:398` (the top accessory lane)

**Done when.** No document content is ever legible through or behind the label.

## 4. Structure — the reading surface

These are ordered by dependency: S1 before S2, S4 before S5.

### S1 — Remove the marker lane

**Evidence.** Shots 1 and 2: `#`, `##`, `$$` hanging left of the column, and a
bare `---` beside the frontmatter block. Shot 3 shows none of them, which is a
separate inconsistency that this change dissolves.

**Why.** They are source spelling rendered into the document view. Heading size
and weight already carry level. The lane's real cost is that it is counted as
part of the column when centring, which pushes the text's optical centre ~20pt
left of the window's — small enough that nobody names it, large enough that the
window never quite settles.

**Change.**
- Remove `#`/`##` heading markers from the rendered view in both Read and Live.
- Remove the `$$` block-math marker.
- Remove the bare `---` frontmatter delimiter. The frontmatter block gets a
  proper boundary in T10 instead.
- Reclaim the lane's width — it is not preserved as empty space.

**Files.** `Engine/DecorationEngine.swift`, `Fragments/MathFragment.swift`,
`Fragments/FrontMatterFragment.swift`, `View/MarkdownContainerView.swift`

**Done when.** No source-syntax glyph appears outside the text column in
Document mode, at any scroll position, with or without a caret.

---

### S2 — A heading-level control, replacing what the markers were doing

**Why.** Removing the markers removes the only visible signal of heading depth
while editing. But the underlying need is not *seeing* the level, it is
*changing* it — and a read-only glyph never served that. Ship the mechanism.

**Change.**

1. **Keyboard, primary path.** `⌘]` promotes, `⌘[` demotes the heading the
   caret is in. `⌘⌥1`–`⌘⌥6` set the level directly. `⌘⌥0` converts to body text.
   Add all of these to the Format menu with visible key equivalents — the menu
   is where this feature gets discovered.
2. **Pointer path.** A small `H2` chip in the left margin, hanging outside the
   text column so **the heading text does not shift by a single pixel** when it
   appears. It appears when the caret enters a heading (Live) or on hover over a
   heading (Read, where restructuring is still a supported activity). Click opens
   a level menu.
3. **Treatment.** `H2`, not `##` — semantic level, not source spelling. This is
   the distinction that makes it read as a control rather than as the marker we
   just deleted. Muted by default, accent on hover.

**Files.** `App/MainMenu.swift`, `Support/Commands.swift`,
`Support/Keybindings.swift`, `MarkdownCore/Restructure.swift`,
`View/MarkdownTextView+Interaction.swift`

**Done when.** With the caret in `## Prose and inline elements`, pressing `⌘[`
makes it `### Prose and inline elements` with no layout jump other than the type
size change; an `H2` chip is visible in the margin and opens a level menu on
click; and nothing appears in the margin when the caret is in a paragraph.

---

### S3 — The section label as a proxy for its heading

Depends on D4 and D5 landing first.

**Change.** Move the label from the window's horizontal centre to the text
column's leading edge — the same x-position the heading it replaces occupied.
Keep the existing treatment: small, muted, sans, with the `⌄` disclosure and the
ancestor path menu.

The current implementation centres on `bounds.width`, which includes both margins
and (until S1) the marker lane. It needs the text column's frame passed down.

**Files.** `Panels/BreadcrumbView.swift:227–241` (the `layout()` override),
`App/DocumentWindowController.swift`

**Done when.** The label's left edge sits exactly on the text column's left
edge at every window width.

---

### S4 — Footnotes in the right margin

**Why.** A footnote reference currently sends the reader to the bottom of the
document, which costs them their place. Setting the note beside its reference
removes the round trip entirely, and gives the empty right margin a reason to
exist that no other candidate matched.

**Change.**
- Footnote bodies render in a reserved lane to the right of the text column,
  vertically aligned to the line carrying their reference.
- Set at ~0.85× body size in the muted ink colour. Quiet enough that the eye
  does not leave the prose to read them.
- When two references are close enough that their notes would collide, push the
  lower note down; never overlap.
- Notes stay in the document's end-matter for export and for Source mode. This
  is a presentation change only.
- The lane is **always reserved**, whether or not any footnote is on screen.
  A lane that appears and disappears would reflow the text column on scroll.

**Files.** `View/MarkdownContainerView.swift`, `Engine/DisplayMap.swift`,
`Engine/DecorationEngine.swift`

**Done when.** In `sample.md`, the footnote body sits beside the line containing
its reference, and scrolling past it causes no reflow of the body text.

---

### S5 — Recentre the column on text-plus-notes

Depends on S1 and S4.

**Why.** With the marker lane gone and a note lane added, "centre the column"
becomes ambiguous. The right answer is to centre the *reading unit* — text
column plus note lane, treated as one block — which is how margin-note book
layouts have always worked. The text sits slightly left of the window's axis and
the notes balance it.

**Change.** Centre `(textColumn + gutter + noteLane)` in the available width.
The density rail is outside this group and stays flush left.

Suggested proportions at a 2000pt window: rail ~44pt flush left; then free
space; then a 660pt text column; a 24pt gutter; a 200pt note lane; then free
space. Tune until the composition reads as balanced with the note lane empty,
since that is its most common state.

**Files.** `View/MarkdownContainerView.swift`

**Done when.** Measured on an empty-margin document, the whitespace to the left
of the text column and to the right of the note lane are equal.

---

### S6 — Rail hover preview shows heading and first sentence

**Evidence.** Shot 3: hovering the rail pops a card reading `> [!NOTE]`,
`> Agents emit these constantly…` — raw markdown, in the rendered view, as a
navigation preview.

**Why.** The card's structure is right — heading trail on top, content below.
Only the content is wrong for the mode.

**Change.** Replace the raw-source body with the section's heading and its first
sentence as plain text. `StructuralZoom.skeletonExtras` already computes exactly
this for zoom level 4; reuse it rather than writing a second extractor. Keep raw
source for the hover in Source Focus, where it is correct.

**Files.** `View/DensityGutterPreviewWindow.swift`,
`MarkdownCore/StructuralZoom.swift`

**Done when.** Hovering the rail over the Callouts section shows
`Callouts` / `Agents emit these constantly, so they get a real treatment: a
coloured left rule and an icon, never a filled box.` with no `>` characters.

## 5. Typography

### T1 — Heading space above and below is too even

**Evidence.** Shot 1: ~65px above `Prose and inline elements`, ~40px below.
A ratio near 1.6.

**Why.** At that ratio a heading floats between two sections instead of binding
to the one it introduces, and sections stop reading as units.

**Change.** Move toward 2.5–3:1. Increase the space *above* rather than closing
the space below — the body needs its breathing room; the section break needs the
weight. Express it as a ratio on the existing modular scale so H1–H4 stay
consistent with each other.

**Files.** `Engine/BlockStyle.swift`

---

### T2 — The paragraph after a list collapses into it

**Evidence.** Shot 1: "These do not, and get a dotted red underline:" sits
noticeably tighter to the list above it than that list sits to its own
introduction. It reads as a fourth bullet for a beat.

**Change.** Paragraph-after-list takes the same block spacing as
paragraph-after-paragraph. Separately, list items need *tighter* internal leading
than the block gap around the list — they are currently close to equal, which is
why the group does not cohere as one object.

**Files.** `Engine/BlockStyle.swift`

---

### T3 — Links: cool hue on a warm page, four species with one style

**Evidence.** Shot 1: a saturated system blue, the only cool colour in the
frame. "relative link to the README" renders as four blue words with visible
breaks in the underline at each link boundary, which reads as damaged text
rather than as four adjacent links.

**Change.**
- Desaturate toward the warm ground, or drop the hue and carry links on a 1px
  underline at ~40% opacity. Either way, set the underline offset so it clears
  New York's descenders — it currently cuts through them.
- Differentiate the four species you actually render — external web, relative
  file, wikilink, reference link — with weight and a single trailing glyph
  (`↗` at 60% for external), not four hues. Hue is already oversubscribed (C1).

**Files.** `Engine/DecorationEngine.swift`, `Theme/StyleSheet.swift`

---

### T4 — Three inline-code treatments, no legible system

**Evidence.** Shot 1: `inline code` in prose gets mono with no chip;
`Package.swift` gets an amber chip. Shot 2: `echo $PATH` gets a grey chip;
`rename()` gets grey again.

**Why.** There is a real system here — prose code, shell, resolved path — and it
is a good one. It is not legible as a system, because nothing tells the reader
the difference is meaningful rather than incidental.

**Change.** Name the tiers and make each derivable from the others: same chip
geometry, differing in exactly one property.

| Tier | Treatment |
|---|---|
| Inline code | Neutral chip, muted ink |
| Resolved path | Neutral chip + 2pt accent leading edge |
| Unresolved path | Neutral chip + dotted underline (see C3) |

**Files.** `MarkdownCore/Extensions/`, `Theme/StyleSheet.swift`

---

### T5 — Inline math outsizes the body; wrapped fractions shrink

**Evidence.** Shot 2: `e^{iπ} + 1 = 0` sits visibly taller than the serif around
it. The summation expression wraps to a second line where the fraction becomes
very small.

**Change.** Scale inline math to match the body's **x-height**, not its point
size. Set a floor on numerator and denominator size so a wrapped fraction stays
readable. Block math is otherwise well handled — S1 removes the orphaned `$$`
marker that currently floats above it.

**Files.** `Fragments/InlineMathDisplay.swift`, `Fragments/MathFragment.swift`

---

### T6 — Completed tasks: let opacity do the work

**Evidence.** Shot 3: full-weight strikethrough through New York at body size.
The line collides with the serif's own horizontal strokes, and the block of four
completed items becomes texture rather than text.

**Change.** Drop completed items to ~55% opacity and thin the strike to 0.5–1px
at ~40%. The dimming says *done*; the strike confirms it. Both at full weight
says it twice.

**Files.** `Fragments/ListOrnamentFragment.swift`

---

### T7 — Callout titles read as an imported system

**Evidence.** Shot 3: sans title over serif body inside the same box. The
contrast is defensible, but the title runs about a point large relative to the
body's x-height so it reads as pasted in rather than composed. The Note box's
bottom padding also looks tighter than the Tip's.

**Change.** Optically size-match the title to the body — match x-heights, not
point sizes. Then equalise vertical padding across all callout kinds; the icon's
height is the likely culprit driving an asymmetric top inset.

**Files.** `Fragments/CalloutFragment.swift`

---

### T8 — One table column absorbs all the slack

**Evidence.** Shot 2, metrics table: `Metric` stretches to eat every spare
point, throwing `Target` and `Measured` to the far right where the eye loses the
row crossing the gap.

**Change.** Size columns to content with a sensible max, then give leftover
width to the table's trailing margin rather than to one column. Add a row hover
tint at 3–4% — it costs nothing at rest and is the cheapest possible fix for
tracking a wide row. Open tables with no zebra striping is right; hover is what
makes it survivable.

**Files.** `Fragments/TableFragment.swift`

---

### T9 — Code blocks have no copy affordance

**Evidence.** Shot 3: the `swift` language label is well placed top-right, but
there is no pointer path to copy the block.

**Why.** Copying a block is the single most common gesture against agent output.

**Change.** Crossfade the language label to a copy control on hover, occupying
the same slot — no new chrome, no collision, and the label already marks the
spot. Confirm the copy with a brief inline state change on the control itself,
not a toast.

**Files.** `Fragments/CodeBlockFragment.swift`

---

### T10 — Frontmatter as a key-value grid

**Evidence.** Shot 1: `title` and `author` pills on the first row, `tags` and
`status` on the second, with the second row overhanging the first on the right.
Neither edge lines up. S1 removes the bare `---` above it.

**Why.** This is key-value data, not a tag cloud. The pill flow fails as soon as
there are eight tags or a long title, which is most real documents.

**Change.** Two-column grid: keys right-aligned in a narrow fixed column at
reduced weight and muted ink; values left-aligned on a shared leading edge.
Close the block with a hairline rule that separates metadata from document body
and doubles as the click target to collapse it. Visible by default — the author
put it there.

**Files.** `Fragments/FrontMatterFragment.swift`

## 6. Discoverability and state

### V1 — Structural zoom is invisible, and a reduced document looks complete

**Why this is the most important item in the plan.** `StructuralZoom.swift`
implements four levels, and level 4 is built precisely for this app's core use
case: every heading, the first sentence of each section, and every code block,
table, math block and task list — "every claim's headline plus all the concrete
artifacts, and none of the connective padding."

Two problems, and the second is a correctness issue rather than a polish one.

**Problem one: nobody can find it.** The only place the feature is announced is
a Tip inside `Docs/sample.md`.

**Problem two: at level 4 the app is hiding paragraphs, and nothing in the frame
says so.** A reader who lands on a zoomed document — or who hits a number key by
accident — sees a document that looks complete and is not. Everything else in
this plan is polish; this one can mislead someone about what a file contains.

**Change, in priority order.**

1. **Elision cue (ship first, independently).** Wherever lines were removed,
   render a visible marker in the flow — a short centred rule, or a muted
   `⋯ 14 lines` — that clicks to expand that region. Plus a persistent, quiet
   indicator whenever zoom ≠ everything, so the state is legible from any
   scroll position.
2. **A control.** A compact stepped control, either in the toolbar or in the
   section-label lane where it sits adjacent to what it acts on. This is the one
   element I would add to the toolbar.
3. **A transient HUD on level change** naming what is kept: *"Skeleton —
   headings, first sentences, artifacts."* The first accidental keypress then
   teaches the model instead of alarming the user.

**Files.** `MarkdownCore/StructuralZoom.swift`, `App/ToolbarControls.swift`,
`App/DocumentWindowController+Actions.swift`, `Engine/DisplayMap.swift`

**Done when.** At level 4, a reader can tell without interacting that content is
hidden, can see roughly how much, and can restore it.

---

### V2 — The toolbar mixes status with action, and omits the state that matters most

**Evidence.** All shots: search, task ring, and overflow sit at equal weight and
spacing. Search is an action; the ring is status. They read as one row of
buttons.

More importantly: the premise of this product is that agent CLIs rewrite the
file underneath you, and nothing in the toolbar reports it. No modified-state
cue, no changed-on-disk cue.

**Change.**
- Separate status from actions with a larger gap before the ring.
- A small dot beside the filename for unsaved changes.
- A visually distinct cue when the file changed on disk since you last read it.

That last one is six points of pixels answering the question the app exists to
answer.

**Files.** `App/ToolbarControls.swift`, `App/DocumentWindowController+Delegates.swift`

## 7. Colour and themes

Do §7 as one pass. The items interact, and split across passes they become three
restyles of the same fragments.

### C1 — Amber is carrying five jobs

**Evidence.** Amber currently marks the task ring, path chips, task checkboxes,
the current-line indicator, and the position dot on the density rail. Two of
those are status, two are interactive state, one is a content annotation. Add
blue for links and Note callouts, yellow for Warning, green for Tip, red for
unresolved paths, plus a full syntax palette, and the page runs seven hues with
no rule governing which means what.

**Change.** One rule, written into the theme tokens:

> **Amber means "you, here, now."** Interactive state, current position,
> selection. Nothing else.

Semantic hues stay reserved for callouts and validity. Content annotation gets
neutral treatment with an accent edge (T4). Everything else is ink.

**Files.** `Theme/StyleSheet.swift`, `Themes/*.json`

---

### C2 — Path chips outweigh the prose they annotate

**Evidence.** Shot 1: in the path tokens list, `Package.swift` reads louder than
"the package manifest".

**Why.** That inverts the hierarchy. The prose is the claim; the path is the
reference. A document full of paths — which is every file this app was built for
— becomes a field of highlights.

**Change.** Neutral chip with the accent on a 2pt leading edge, per T4. Also give
the chip a trailing margin — the em dash currently runs straight into it.

**Files.** `MarkdownCore/Extensions/`, `Theme/StyleSheet.swift`

---

### C3 — Red is too alarming for an unresolved path

**Evidence.** Shot 1: `src/auth/session.ts:42` and
`Sources/MarkdownCore/Imaginary.swift` get a dotted red underline.

**Why.** An unresolved path is usually not an error. It may point into another
repository, or be illustrative, or simply not exist yet. Red is the app's
strongest alarm colour and it is being spent on a routine condition — in a
document type where unresolved paths are common.

**Change.** Desaturate to a muted ink dotted underline. Keep red for genuine
error states. The distinction the reader needs is *this one is not clickable*,
not *something is wrong*.

**Files.** `Theme/StyleSheet.swift`, `MarkdownCore/Extensions/`

---

### C4 — Paper light needs its own alphas, not the dark theme's

Two treatments will break first when composited over the light ground:

- **Callout tints.** A 4% white tint on near-black is nearly invisible; a 4%
  black tint on paper is a visible grey box. The subtlety that makes the dark
  callouts work reads as a heavy card on light.
- **Code and chip tints.** Same problem, more acute — a tint that whispers on
  `warm-dark` shouts on `paper-light`.

**Change.** Define tints as separate per-theme tokens with different alpha
values, never one alpha composited over two grounds. Same for the table rule and
the section-label scrim (D5).

**Files.** `Themes/paper-light.json`, `Themes/warm-dark.json`,
`Theme/StyleSheet.swift`

---

### C5 — Measure the low-contrast elements

The `Docs` subtitle, the table header grey, the code-block language label, and
the rail marks all sit low enough in the dark theme to look sub-4.5:1 by eye.

Several are not body text, so AA is arguably not required — but the language
label and table headers carry real information.

**Change.** Measure rather than judge by eye, assign each element a tier, and
confirm Increase Contrast lifts the whole set including the rail, which is the
element most likely to have been missed.

**Files.** `Theme/ThemeValidation.swift`

---

### C6 — The current-line indicator

**Evidence.** Shot 1: a small amber dotted vertical mark in the left margin
beside "with emphasis, both at once…".

**Change.** Under C1 amber is correct here — this is "you are here". But the
dotted treatment reads as a rendering artifact at this size. Make it a solid
hairline. Note that S1 reclaims the margin space it currently sits in, so its
x-position needs revisiting alongside S5 regardless.

**Files.** `Engine/DecorationEngine.swift`, `View/MarkdownContainerView.swift`

## 8. Sequencing

Each pass is shippable on its own.

### Pass A — defects and rhythm
`D1 D2 D3 D4 D5 T1 T2 T6`

No design decisions required; the target state is specified for every item.
Individually trivial, collectively the app reads noticeably sharper.

### Pass B — structure
`S1 S2 S3 S4 S5 S6 T10`

The reading surface. Order matters: S1 → S2, then S4 → S5. S3 depends on D4/D5
from Pass A. T10 rides along because S1 removes the frontmatter delimiter and
leaves the block needing a boundary.

This is where the app stops looking like a good markdown viewer and starts
looking like the only one built for this job.

### Pass C — colour, themes, and the fragments they touch
`T3 T4 T5 T7 T8 T9 C1 C2 C3 C4 C5 C6`

One pass, both themes. The typographic items are here rather than in Pass A
because they live in the same fragments as the colour work, and splitting them
means restyling the same files twice.

Do C1 first — the amber rule determines T3, T4, C2, and C3.

### Pass D — discoverability
`V1 V2`

Last because V1's control wants the section-label lane from Pass B.

**Exception: `V1` step 1 — the elision cue — should ship in Pass A.** It is not
polish. Until it exists, a zoomed document can misrepresent what a file
contains, and that is the only item in this plan capable of misleading someone.

## 9. Open questions

None blocking. Three worth a decision when the relevant pass starts.

1. **S4 — note lane width on narrow windows.** Below some width the note lane
   has to collapse and footnotes fall back to end-matter. Where is that
   threshold, and does the text column recentre when it does? Recommendation:
   collapse below ~1100pt, and yes, recentre — a reflow at a window-resize
   boundary is acceptable in a way that a reflow on scroll is not.

2. **S2 — does the `H2` chip appear on hover in Read mode?** The argument for is
   that restructuring is a Read-mode activity. The argument against is that it
   puts a control in the calmest view. Recommendation: yes, but only on hover
   directly over the heading, never on hover anywhere in its line.

3. **V1 — where does the zoom control live?** Toolbar is more discoverable; the
   section-label lane is more adjacent to what it acts on and keeps the toolbar
   at three items. Recommendation: section-label lane, with a Format-menu entry
   carrying the key equivalents for discovery.

## 10. Not recommended

Recorded so they are not re-proposed.

- **Expanding the density rail to full height.** It would become a minimap and
  lose the thing that makes it good — that the mark cluster's position in the
  window *is* the scroll position.
- **A permanent outline sidebar.** The rail plus its hover preview (S6) covers
  navigation. A permanent sidebar makes every short document feel like a wiki
  and spends the width that S4 uses better.
- **Keeping `##` as a read-only marker anywhere.** Superseded by S2. If a level
  indicator is visible, it must be editable.
- **Filling both margins.** Only the right margin gets a job (S4). The left is
  breathing room and the rail's home; symmetry here would crowd the column from
  both sides.
